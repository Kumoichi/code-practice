このファイルはコンパイルされません（.go拡張子ではありません）。
「Badの設計ではMockを差し込めない」ことを示すためのサンプルです。

box_usecase.go で、BoxUseCase は以下のように定義されています。

    type BoxUseCase struct {
        repository *persistence.BoxRepository
    }

    func NewBoxUseCase(repository *persistence.BoxRepository) *BoxUseCase {
        ...
    }

NewBoxUseCase の引数は "*persistence.BoxRepository" という
具体的な型で固定されています。interfaceではありません。

ここで、good側と同じようにMockを自作してみます。

    type MockBoxRepository struct {
        Box *persistence.Box
        Err error
    }

    func (m *MockBoxRepository) Find(id int) (*persistence.Box, error) {
        if m.Err != nil {
            return nil, m.Err
        }
        return m.Box, nil
    }

このMockを使ってUseCaseのテストを書こうとすると、次のようになります。

    // このコードはコンパイルできない:
    //
    // useCase := NewBoxUseCase(
    //     &MockBoxRepository{
    //         Box: &persistence.Box{ID: 1, Number: 5},
    //     },
    // )
    //
    // コンパイルエラー:
    // cannot use &MockBoxRepository{…} (value of type *MockBoxRepository)
    // as *persistence.BoxRepository value in argument to NewBoxUseCase
    //
    // なぜなら NewBoxUseCase は *persistence.BoxRepository という
    // 「PostgreSQLの実装そのもの」を要求しており、
    // MockBoxRepository が同じメソッドセットを持っていても
    // 型としては全くの別物だからです。
    //
    // interfaceを挟んでいれば「Find(id int) (*Box, error) を満たすか」
    // だけが問われますが、Badでは「persistence.BoxRepositoryという
    // 具体的な構造体そのものか」が問われてしまいます。

この結果、Bad側でUseCaseをテストするには、実際にPostgreSQLへ接続する
box_usecase_test.go のような方法しか残されていません。
